# 项目重组总结

> 版本：v1.0（2026-08-08）
> 本文件是第二阶段（产品需求符合性审查与项目规划）的最终总结，汇总全部交付物与核心结论。

## 1. 当前项目真实状态

- **形态**：零构建纯前端演示原型（原生 HTML/CSS/JS + LocalStorage + Nginx 静态托管），无后端、无认证、无测试。
- **代码基线**：Git 2 个提交（2026-08-06）；工作区另有 2026-08-08 未提交的患者端改版（首页 2×2 服务入口、预约表单、医院列表/详情、特色 Tab、登录入口修复）。
- **架构**：data.js（数据）→ store.js（CareStore 状态层）→ app.js（外壳）→ patient.js/admin.js（页面）→ workflow.js（覆盖层，承载最新业务闭环）。
- **核心矛盾**：患者端改版（未提交）与 workflow/CareStore 既定闭环（已提交）未完成集成——新 UI 可用但不合规（自动随机派单、绕过状态机），合规流程不可达（我的需求/陪诊进度/医院介绍/OCR 无入口）。
- **数据事实**：`CareStore.version = 2`；主键 `huwuyou_store_v1`；状态机仅允许"待处理→已分配→服务中→已完成"（待处理/已分配→已取消）；但代码中仍存在"已对接"创建路径（孤儿状态，订单会卡死）；医院库 23 家全为上海，旧数据/AI 别名仍引用北京。

## 3. 最大差距

**产品流程断裂**：当前"立即预约"在已部署版本中直接进入陪诊师选择（与用户预期相反）；工作区版本虽改为患者表单，却用"自动随机派单 + 直接已分配"替代，绕过了"后台审核 → 管理员配置陪诊师 → 患者查看"的既定闭环（REQ-04/05/08/11）。

**结构性根因**：患者端改版与 workflow 覆盖层没有完成对接，导致系统同时存在"新流程不合规"与"合规流程不可达"两种缺陷；叠加"已对接"孤儿状态、价格/服务两套体系、北京/上海数据混用，形成演示级系统性穿帮风险。

## 6. 工作要求

1. **代码是唯一事实源**：任何文档（含本文件）与代码冲突时，以代码为准并记录差异。
2. **先分析后动手**：分析/审查类任务只输出文档，不修改代码；开发类任务按路线图与 agent.md 执行。
3. **不假设功能存在**：引用任何能力前先全局检索验证（含 workflow 覆盖与内联事件）。
4. **状态唯一、价格唯一、医院唯一**：状态走 `CareStore.transitionNeed`；价格走 `PriceTable`；医院走 `CareStore.state.hospitals`；禁止并行体系。
5. **文档归档制**：不删除文档；过时方案移入 `docs/archive/`；变更同步更新 README、差距分析、路线图。
6. **演示边界**：不保存真实敏感资料；不引入后端/依赖；不宣称生产能力。
